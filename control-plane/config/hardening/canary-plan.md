# 灰度上线计划（设计 §10 阶段 3 / add-hardening-rollout §5）

> 灰度按「风险由低到高」放量。每阶段观察期 ≥1 周，观察指标全绿且演练门禁通过后，方可进入下一阶段。
> 上线评审（§5.3 / V.1）须逐项确认：混沌、性能、升级回滚、备份演练、安全基线全部通过。

## 阶段 1：内部中间件（最低风险）

- 对象：团队内部、低 SLA、易重建的无状态中间件（如缓存、日志采集侧车）。
- 存储：thin 即可，不涉及关键数据。
- 目标：验证纳管、容量治理、告警闭环在真实负载下的稳定性。

## 阶段 2：多副本无状态业务

- 对象：多副本、可重建的业务服务。
- 验证：单节点故障（§9.2）下重建流程顺畅；drift/orphan-gc 无虚警。

## 阶段 3：有状态 / 关键业务（最高风险）

- 对象：数据库、关键有状态服务。
- 前置：critical 业务**默认 thick LV**（§9.1 规避 thinpool 打满风险）；备份演练（add-backup-restore）每季度通过；恢复 RTO/RPO 达标。
- 验证：节点退役（§9.4）、磁盘损坏（§9.3）剧本在该类业务上演练通过。

## 观察指标（每阶段持续采集）

| 指标 | 告警阈值参考 |
| --- | --- |
| 告警量（Critical/Warning） | 与设计 §8 矩阵比对，无异常新增 |
| 容量水位（tier 使用率） | 分级超分阈值内，无越限 |
| drift 检出 | 0 误报（break-glass 除外） |
| 任务失败率（StorageTask） | 趋零，失败均有审计与处理 |
| 恢复演练通过率 | 100%（每季度） |
| 数据面独立性 | 控制面/Agent/Webhook 宕机时已有卷 IO 零影响（§1.2） |
