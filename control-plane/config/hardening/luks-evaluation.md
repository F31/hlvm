# LUKS 可选项评估结论（设计 §6.7 / §11 数据安全 / add-hardening-rollout §4.3.2）

## 结论

**POC 与 MVP 阶段不将 LUKS 作为默认。** 仅在出现明确合规要求（静态数据加密）时启用，且须先完成密钥管理落地评估。理由如下。

## 方案

LUKS 置于 LV 之上（或 TopoLVM 支持的加密方式），对本地盘上的业务数据做静态加密。
密钥管理（KMS / Vault）须纳入范围评估——加密卷的挂载重加密依赖密钥可用性与轮换策略。

## 影响与风险

| 维度 | 影响 |
| --- | --- |
| 性能 | 加密/解密带来 CPU 开销与写延迟增量，须在 perf-baseline-report 中单独测项（§2） |
| 运维 | 密钥丢失 = 数据不可恢复；需密钥备份与应急解密流程 |
| 恢复 | 节点故障后重建加密卷需密钥注入；与 §9.2 隔离期/重建流程耦合 |
| 复杂度 | 与漂移检测、orphan-gc、退役擦除（§4.3.1 已审计）交互，增加状态机分支 |

## 启用前置条件（决策门）

1. 明确合规条款要求静态加密（否则不引入）。
2. 密钥管理方案（KMS/Vault 集成、轮换、备份、应急）已落地并演练。
3. 性能基线测得加密开销在可接受区间（写入 perf-baseline 回归基线）。
4. 加密卷的故障/退役/恢复剧本已补充进 §9 Runbook 并演练通过。

> 未满足上述任一条件前，磁盘退役仍按 §4.3.1 的 secure-erase 审计路径执行（已落地），不依赖 LUKS。
