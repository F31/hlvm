# 自研本地存储平台设计方案（TopoLVM 底座 + 自研控制面 + 节点 Agent）

> 版本：v1.1（评审优化版）｜ 2026-10-15 ｜ 基于 v1.0 评审后重写
> 目标：基于 TopoLVM 构建轻量、高性能、具备磁盘生命周期与容量治理能力的本地存储平台（暂名 hlvm）
> 核心决策：**CSI 复用 TopoLVM（跟随上游）｜控制面自研（Go）｜节点 Agent 语言经 POC 决策门后定稿（默认 Rust）**
> 阅读指引：变更与评审意见见**附录 B**；标注 `【待核实】` 的内容依赖上游版本或外部事实，立项前必须核对。

---

## 1. 设计原则

1. **CSI 不出自研代码**：TopoLVM 的 CSI controller / node / lvmd 直接使用上游镜像，私有 patch 控制在 0–2 处。
2. **差异化全部在旁路**：磁盘纳管、SMART、thinpool 保护、生命周期控制器均以独立组件 + CRD 实现。
3. **能上上游就上上游**：确需增强 TopoLVM 的能力优先提 PR；不被接受时才 fork。
4. **数据面独立于控制面（新增）**：控制面、Agent、Webhook 任何一个整体宕机，**已有卷的 IO、挂载、扩容之外的存量业务不受影响**。这是所有设计取舍的底线。
5. **每一层只有一个写者（新增）**：LV 级由 lvmd 写；PV/VG/thinpool 级由 Agent executor 写；其他任何组件、人工操作均视为"漂移"，由 drift 检测发现并告警。
6. **破坏性操作必须人工确认（新增）**：wipe、vgreduce、LV 删除、数据迁移，平台只做"预检 + 建议 + 执行"，不做"自动决定"。
7. **故障剧本化**：节点故障、坏盘、thinpool 打满有内建 Runbook，并经混沌演练验证。
8. **一切性能与可靠性指标以 POC 实测为准（新增）**：文档中不预设"接近裸盘""零开销"结论。

## 2. 总体架构

```
┌────────────────────────────── 控制面（Go）────────────────────────────────┐
│ storage-controller（Deployment ×2，leader election）                       │
│   disk-ctrl │ vg-ctrl │ capacity-ctrl │ lvmd-config-ctrl │ lifecycle-ctrl  │
│   snapshot/backup-ctrl │ orphan-gc │ drift-detector │ audit                │
│ storage-webhook（独立 Deployment ×3，无 leader，PDB + 反亲和）              │
│   PVC create/expand 准入 │ Pod 调度约束注入 │ 删除保护                      │
└──────┬──────────────────────────────┬─────────────────────────────────────┘
       │ CRD（Disk/VG/ThinPoolPolicy/StorageTask/StorageNodeOps）
┌──────▼──────────┐  ┌───────────────▼──────────────┐  ┌──────────────────┐
│ TopoLVM（上游）  │  │ 节点侧（同一二进制，两个 DS）   │  │ 平台 UI / OpenAPI │
│ controller/node │  │ storage-agent  （特权，读写）   │  └──────────────────┘
│ lvmd（LV 级写者）│  │ storage-exporter（非特权，只读）│
└──────┬──────────┘  └───────────────┬──────────────┘
       └───────────────┬─────────────┘
                lvm2 / mdadm / smartctl / nvme（宿主机工具，统一入口）
                       节点磁盘 / VG / thinpool
```

### 组件清单

| 组件 | 语言 | 部署形态 | 职责 | 来源 |
| --- | --- | --- | --- | --- |
| topolvm-controller / topolvm-node / lvmd | Go | TopoLVM 官方 Helm | CSI 供给、扩容、快照、LV 管理 | **上游** |
| 容量感知调度 | — | 优先使用 K8s 原生 CSIStorageCapacity；scheduler-extender 仅在上游版本仍要求时启用 `【待核实】` | 调度时容量过滤 | 上游 |
| storage-controller | Go | Deployment ×2，leader election | 全部 CRD 控制器、lvmd 配置渲染、GC、审计 | 自研 |
| storage-webhook | Go | **独立** Deployment ×3，active-active | 准入校验，不含任何业务计算 | 自研 |
| storage-agent | Rust（见 §5.5 决策门） | DaemonSet，特权 | 磁盘发现、预检、executor（唯一 PV/VG/pool 写路径） | 自研 |
| storage-exporter | 同一二进制 `--mode=exporter` | **独立 DaemonSet**，非特权，只读挂载 | 指标采集 | 自研 |

> 修正 v1.0：二进制合并**不等于**最小权限。权限由部署形态决定：exporter 使用独立 DaemonSet、独立 ServiceAccount、只读挂载、无 privileged，才真正满足最小权限。

### 2.1 与 TopoLVM 的集成契约（新增，v1.0 缺失）

自研控制面与 TopoLVM 的衔接点必须显式定义，否则"旁路"无法落地：

| 衔接点 | 做法 |
| --- | --- |
| device-class 配置 | TopoLVM 的 thin/thick、`thin-pool`、`overprovision-ratio` 等均在**每节点 lvmd 配置**中。新增 `lvmd-config-ctrl`：由 VG CRD 渲染各节点 lvmd ConfigMap，变更经灰度 + 滚动重载（是否支持热加载 `【待核实】`）。 |
| LV 与 PV 对账 | 读取 TopoLVM 的 `LogicalVolume` CR 与 PV，而非解析 `lvs` 文本；与节点 `lvs` 结果做三方对账（CR / PV / 实际 LV）。 |
| 容量数据源 | 使用 `CSIStorageCapacity` 与 lvmd 上报；自研指标只做补充，口径冲突时以实测 `lvs/vgs` 为准。 |
| StorageClass 参数 | provisioner 为 `topolvm.io`，参数键 `topolvm.io/device-class`（v1.0 写为 `topolvm.cybozu.com/...cybozu.io`，已过时且前后不一致）`【待核实具体版本】`。 |
| LVM 并发 | Agent 与 lvmd 同机操作同一 VG，必须共享宿主机 LVM 锁目录并通过统一入口调用宿主机 lvm（见 §5.3）。 |

## 3. CRD 设计

API Group：`storage.example.io/v1alpha1`（上线前替换，并确定 Kind 命名以避免与 OpenEBS `BlockDevice` 等冲突，建议 `NodeDisk` / `NodeVG`，下文沿用 `Disk` / `VG`）。所有对象 cluster-scoped。

### 3.1 Disk（磁盘）

由 agent 自动发现创建。**身份用 WWN/serial，不用设备名**（`/dev/nvme0n1` 重启可能漂移；换盘同槽位不应复用旧对象）。

```yaml
apiVersion: storage.example.io/v1alpha1
kind: Disk
metadata:
  name: node37-s5yjnx0r123456            # {node}-{serial/wwn 短名}，非设备名
  labels:
    storage.example.io/node: node37
    storage.example.io/media: nvme       # nvme | ssd | hdd
    storage.example.io/health: healthy   # healthy | warning | critical | failed
spec:
  nodeName: node37
  adopt: false                           # 人工/平台置 true 才进入纳管流程
  confirmSerial: ""                      # 破坏性操作前必须与 status.serial 一致（防误选盘）
  wipePolicy: secure-erase               # none | zero | secure-erase
status:
  identity: { serial: S5YJNX0R123456, wwn: "eui.xxxx", model: "Samsung PM9A3", byId: /dev/disk/by-id/nvme-... }
  currentDevice: /dev/nvme0n1            # 仅作展示，操作一律走 by-id
  capacityBytes: 1920383410176
  phase: Candidate    # Discovered → Candidate → PreChecked → Wiped → InVG → Draining → Removed
  health: healthy
  smart:
    lastProbeTime: "2026-10-15T08:00:00Z"
    overallStatus: passed
    criticalWarning: 0                   # NVMe critical_warning 位图
    availableSparePercent: 100
    percentUsed: 12
    temperatureCelsius: 41
    mediaErrors: 0                       # 以增量判定，见 §8
    unsafeShutdowns: 2
  occupiedBy: none                       # none | filesystem | lvm-pv | md | mpath | holder | unknown
  isSystemDisk: false
  raid: { memberOf: "", degraded: false }
  vgRef: ""                              # 所属 VG
  conditions: []                         # Ready / Healthy / InVG
```

设计要点：

- **拆分两个维度**（v1.0 混用）：`phase` 是生命周期，`health` 是健康度，互不覆盖。
- **推进由意图驱动**：`Candidate → PreChecked` 由 agent 预检自动完成；`PreChecked → Wiped → InVG` 需 `spec.adopt=true` 且被 VG 引用；`wipe` 额外要求 `confirmSerial` 匹配。
- **预检规则（agent 内引擎）**：系统盘（根/boot/swap/kubelet 数据目录所在盘及其 holders）、存在 fs/LVM/md 签名、被 multipath 或 device-mapper 持有、已是 PV、SMART failed、容量/介质不符 tier。任一命中 → 不可进入 `PreChecked`。
- **etcd 写放大控制**：SMART 全量采样只进 Prometheus；CRD status 仅在 `health/phase` 变化或每 10 分钟低频刷新，避免 `节点数×盘数×每分钟` 的状态写。
- **热插拔**：除周期扫描，监听 udev 事件触发即时重扫。

### 3.2 VG（卷组）

```yaml
apiVersion: storage.example.io/v1alpha1
kind: VG
metadata:
  name: vg-nvme-node37                   # vg-{tier}-{node}
  labels: { storage.example.io/tier: nvme }
spec:
  nodeName: node37
  tier: nvme                             # tier ↔ StorageClass ↔ lvmd device-class；VG 本身不绑 SC
  layout: pooled                         # pooled | per-disk（见下）
  redundancy: none                       # none | hw-raid | md-raid1 | lvm-raid1(experimental)
  disks: [node37-s5yjnx0r123456, node37-s5yjnx0r654321]
  thinPool:
    name: tp-nvme-node37
    initialSizePercent: 80               # 初始占 VG 比例；VG 其余部分为扩容缓冲
    maxSizePercent: 95                   # 自动扩容上限，保留 5% 给 metadata 增长与救急
    metadataSize: 8Gi                    # 按池大小与 chunk 计算，见 §3.3
    chunkSize: 128Ki                     # 在 POC 中按负载定标
    overprovisionRatio: 1.5              # 分级默认值，见 §6
  operations:
    removeDisks: []
status:
  vgExists: true
  vgUUID: "..."
  totalBytes: 0
  freeBytes: 0
  thinPool:
    currentSizeBytes: 0                  # 自动扩容的结果写 status，不回写 spec
    dataPercent: 42.3
    metadataPercent: 8.1
    provisionedBytes: 0
    state: healthy                       # healthy | warning | critical
    outOfSpace: false                    # pool 是否已进入 out-of-data-space 模式
  capacityStatus: available              # available | pressure | locked
  lastDriftCheck: "..."
  pendingOps: []
```

设计要点：

- **v1.0 的数学矛盾（已修正）**：原设计 `sizePercent=90`、`autoExpand.maxSizePercent=98`，数据区 85% 时最多只能把池扩大约 9%，使用率只降到约 78%，根本达不到 `targetPercent=65`。新设计初始 80%、上限 95%：以 100G 的 VG 为例，池 80G 用到 70% 触发扩容 +20%（受上限约束扩到 95G），使用率回落到约 59%。**自动扩容的本质是有限缓冲，不是容量来源**，真正的容量保护是超分比例 + 锁 + 告警 + 人工扩盘。
- **spec/status 分离**：控制器不得回写 `spec`（避免 GitOps 漂移冲突）。
- **layout 策略**：`pooled`（多盘一个 VG，容量灵活，但**任一盘损坏整个 VG 全部 LV 丢失**，故障率随盘数线性上升）；`per-disk`（一盘一 VG 一 device-class，爆炸半径限于单盘，代价是容量碎片与调度粒度）。**无 RAID 的 tier 默认 `per-disk`，有 RAID 的才允许 `pooled`**。
- **RAID 位置**：推荐在 LVM 之下做（硬件 RAID 或 mdadm 形成单一 PV），工具链最成熟；LVM RAID 仅作实验选项（需验证 thin-pool 数据/元数据均带冗余、与 TopoLVM 的兼容性 `【待核实】`）。RAID 状态由 Disk/VG status 统一表达，不再在两处各有一份字段。
- **删盘保护**：移除盘前校验无 LV 占用、不会导致冗余丧失；否则拒绝并写入 `status.pendingOps` 原因。
- **加盘即扩容**：`spec.disks` 增加 = `pvcreate + vgextend`；扩容 thinpool 由 capacity-ctrl 或 dmeventd 完成。

### 3.3 ThinPoolPolicy（容量策略，集群级单例，可按 tier 覆盖）

```yaml
apiVersion: storage.example.io/v1alpha1
kind: ThinPoolPolicy
metadata: { name: default }
spec:
  thresholds:
    autoExtendPercent: 70        # dmeventd 触发扩容
    autoExtendStepPercent: 20
    warningPercent: 75
    criticalPercent: 85          # → locked
    unlockPercent: 80            # 滞回，避免锁在边界反复抖动
    metadataWarningPercent: 50
    metadataCriticalPercent: 75
  forecast:
    timeToFullWarning: 24h       # 按增长速率预测，早于阈值告警
    timeToFullCritical: 4h
  lock:
    blockNewPVC: true
    blockPVCExpansion: true      # v1.0 遗漏：存量卷扩容同样会吃掉 pool
  requireFreeVGSpace: 10Gi       # 不足则转人工工单
  alertChannels: [webhook, mail, sms]
```

关键点：

- **扩容第一道防线交给 LVM 原生 dmeventd**（`activation { thin_pool_autoextend_threshold / thin_pool_autoextend_percent }`，需宿主机 `dmeventd` 监控开启）。它由内核事件驱动，秒级响应；而控制面按 60s 周期采集再决策，对 fio 类突发写入来不及。capacity-ctrl 负责策略下发（渲染 lvm.conf）、状态评估、告警、锁与审计，**不依赖它做秒级动作**。
- **capacityStatus 映射**：`<75% available` → `75–85% pressure` → `≥85% 或 metadata≥75% 或 outOfSpace locked`；回落到 `unlockPercent` 以下才解锁。
- **metadata 规划**：`metadataSize` 与 `chunkSize`、池大小、快照数量相关，需在 POC 用真实卷数量与快照密度定标；元数据可在线扩，上限与 `thin_check` 修复步骤纳入 Runbook。
- webhook **只读 VG status**，不做实时计算。

### 3.4 StorageTask（节点任务，新增）

取代 v1.0 的"annotation 指令队列"：annotation 无 spec/status 语义、无法做幂等与 TTL，也难做权限隔离。

```yaml
kind: StorageTask
metadata: { name: task-7f3a... }       # 稳定 taskID
spec:
  nodeName: node37
  type: wipe | pvcreate | vgcreate | vgextend | vgreduce | thinpool-extend | md-repair
  target: { diskRef: node37-s5yjnx0r123456 }
  confirmSerial: S5YJNX0R123456
  dryRun: false
  approvedBy: alice                    # 破坏性任务必须有审批人（由 webhook 校验）
  ttl: 1h
status:
  phase: Pending | Running | Succeeded | Failed | Unknown
  startedAt: ...
  result: ...
```

- **节点级权限隔离**：agent 的 ServiceAccount 只能读写 `spec.nodeName` 等于自身节点的 Task/Disk（通过 ValidatingAdmissionPolicy + 节点绑定 token 实现，类似 NodeRestriction），一个节点被攻破不能操作其他节点的盘。
- **幂等**：以 taskID 去重，agent 落盘执行日志；崩溃恢复后"已执行未回执"的任务重新探测实际状态后补回执，不重复执行。

### 3.5 StorageNodeOps（节点运维剧本）

```yaml
kind: StorageNodeOps
metadata: { name: retire-node37-20261015 }   # 允许一个节点多次操作，不再"一节点一对象"
spec:
  nodeName: node37
  operation: retire | isolate | recover-disk
  force: false
status:
  phase: validate | drain | wait-pvc-cleanup | wipe | done
  blockingPVCs: ["mysql/mysql-data"]
```

## 4. Webhook 与调度约束（重写，v1.0 存在可行性缺陷）

**v1.0 缺陷**：PVC 在 `WaitForFirstConsumer` 模式下创建时尚未选定节点，webhook 无法"读取对应 VG 的状态"；同时 `FailurePolicy=Fail` 且作用于全部 PVC，webhook 故障会阻塞整个集群的 PVC 创建；`tier-nvme-ready` 标签没有任何消费方。

新设计分三层：

1. **PVC 准入（tier 级）**：仅对使用本平台 StorageClass 的 PVC 生效（用 `matchConditions` CEL 过滤，K8s ≥1.28 `【待核实集群版本】`）。判定的是"该 tier 是否存在至少一个可用节点"，而非某个具体 VG；覆盖 **CREATE 与扩容 UPDATE**。
2. **节点级约束（调度层）**：capacity-ctrl 给被锁节点打 `storage.example.io/<tier>-locked=true`，由 Pod 变更 webhook（或 Scheduling Gate）为引用本平台 PVC 的新 Pod 注入 nodeAffinity 排除被锁节点。该方案需在 POC 验证，备选为依赖 CSIStorageCapacity 的容量过滤 + 业务侧告警。
3. **静态规则用 ValidatingAdmissionPolicy**：SC 白名单、reclaimPolicy、必填的副本数声明标签等不需要自研 webhook。

可用性要求：

- webhook 独立部署 ×3，PDB + 反亲和 + 低延迟（超时 ≤3s）。
- **FailurePolicy 分级**：安全类（删除保护）= Fail，仅作用于本平台对象；容量类拦截 = Ignore，并在 webhook 异常时由 capacity-ctrl 告警兜底（容量拦截缺失的风险小于阻塞全集群的风险）。
- 拒绝信息面向租户，不暴露节点名/VG 名等内部细节，详细原因写审计与告警。

## 5. 节点 Agent 设计

### 5.1 模块

```
src/
  main.rs        # --mode=agent | exporter | doctor
  discovery/     # /sys/block、lsblk --json、udev 事件
  smart/         # NVMe（nvme-cli / ioctl）与 SATA/SAS（smartctl --json）统一抽象
  precheck/      # 规则引擎：系统盘、签名、holders、multipath、已用 PV
  executor/      # StorageTask 消费者（唯一 PV/VG/pool 写路径）
  lvm/           # 宿主机 lvm 命令封装（统一入口、白名单、JSON 输出）
  reporter/      # CRD status 低频更新 + /metrics
  doctor/        # 诊断打包
```

### 5.2 关键设计

1. **读写分离靠部署，不靠代码**：exporter 与 agent 为不同 DaemonSet（§2）。写操作只来自 `StorageTask`，不接受任何外部直接调用。
2. **操作安全**：命令一律以 argv 数组执行，**禁止 shell 拼接**；设备路径只接受 `/dev/disk/by-id/...` 并做格式校验；每个破坏性动作执行前二次读取实际状态（serial 匹配、无签名/无持有者、非系统盘）；支持 `dryRun`。
3. **幂等与对账**：见 §3.4。
4. **SMART 抽象**：`enum Health { Healthy, Warning, Critical, Failed }`；阈值表放 ConfigMap 并热加载；NVMe 关注 `critical_warning`、`available_spare`、`percentage_used`、`media_errors` **增量**；SATA 关注 reallocated / pending / offline uncorrectable。
5. **资源**：初始建议 requests 50m/64Mi、limits 200m/256Mi，**以 POC 实测（多盘节点、smartctl fork 峰值、日志量）为准**，v1.0 的 128Mi 为经验猜测。

### 5.3 LVM 执行环境（新增）

容器内直接调用 LVM 有已知坑：lvm2 版本与宿主机内核 device-mapper 不匹配、udev 同步、锁目录不共享。要求：

- 通过 `chroot /host`（或 nsenter）调用**宿主机** `lvm`，与 lvmd 使用同一套工具与锁（`/run/lock/lvm`）。
- 统一使用 `--reportformat json` 解析；解析失败一律视为"未知"，不得推断。
- 在宿主机用 `lvm.conf devices {}` / devices file 限定 LVM 只扫描纳管盘，避免扫描到 LV 内嵌套的 LVM 或其他卷组。
- dmeventd 的启用与 `thin_pool_autoextend_*` 配置由 agent 管理并校验。

### 5.4 exporter 指标

```
storage_disk_smart_health{node,device,media}              # 0/1/2/3
storage_disk_smart_temperature_celsius{node,device}
storage_disk_media_errors_total{node,device}
storage_disk_available_spare_percent{node,device}
storage_disk_percent_used{node,device}
storage_vg_total_bytes / storage_vg_free_bytes{node,vg}
storage_thinpool_data_percent{node,vg}
storage_thinpool_metadata_percent{node,vg}
storage_thinpool_provisioned_bytes{node,vg}
storage_thinpool_overprovision_ratio{node,vg}
storage_thinpool_out_of_space{node,vg}                    # 0/1
storage_raid_degraded{node,md}
storage_agent_last_scan_timestamp_seconds{node}
storage_agent_task_failures_total{node,task_type}
storage_drift_detected{node,vg,kind}                      # CR/PV/LV 对账不一致
```

控制面与 webhook 另有 reconcile 错误数、准入延迟、拒绝计数。与 TopoLVM 自带 `topolvm_*` 指标并存时，**仪表盘与告警统一使用本方案指标**，避免双口径。LV 级指标只做 Top-N，避免基数爆炸。

### 5.5 实现语言决策门（新增）

v1.0 "Rust 用在刀刃上" 的理由偏弱：agent 的主要工作是 fork lvm/smartctl 并解析输出，Rust 在内存占用上的优势有限，而 Go 版 agent 可以直接复用 TopoLVM lvmd 的 LVM 命令封装与 controller-runtime 生态，双语言工具链会增加长期维护成本。建议在 POC 阶段（§10）做决策：

- 团队具备 Rust 工程能力、且对常驻内存/镜像体积有硬指标 → 保持 Rust。
- 否则采用 Go 实现 agent，仅在发现明确性能/安全收益处再引入 Rust。

无论选哪个，exporter / agent 对外的 CRD 契约与指标不变，决策不影响其他组件。

## 6. StorageClass 与使用规范

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: topolvm-nvme
provisioner: topolvm.io
parameters:
  csi.storage.k8s.io/fstype: xfs
  topolvm.io/device-class: nvme
reclaimPolicy: Retain               # 数据库默认；注意必须配套 orphan-gc，见 §7
allowVolumeExpansion: true
volumeBindingMode: WaitForFirstConsumer
```

**分级超分策略（修正 v1.0 默认 3.0 与"关键业务 ≤2"的矛盾）**

| 等级 | 适用 | overprovisionRatio | 说明 |
| --- | --- | --- | --- |
| critical | 生产数据库、消息队列 | 1.0（等价厚置备）或使用 thick device-class | 推荐关键业务直接走 thick，规避 thin 的 pool 打满风险 |
| standard | 一般有状态中间件 | 1.5 | 默认 |
| dev/test | 测试环境 | 3.0 | 强制告警 |

使用规范：

1. 单副本本地卷，盘损即丢数据——**仅限多副本业务**（MySQL 主从、Redis Cluster、ES、Kafka 等）。
2. 单实例数据库禁止使用；PVC 需带 `storage.example.io/replicas` 声明，选型评审留痕，**默认只提示不强拦**（避免误杀 StatefulSet）。
3. 文件系统启用 `discard` 或周期 `fstrim`，确保删除数据能归还 thinpool。
4. **快照不是备份**：快照与源卷同盘同 VG，且 COW 增长会消耗 thinpool，容量规划需计入。生产 PVC 默认开启备份到对象存储。
5. 备份前提供数据库一致性 pre-hook（flush/锁表）。
6. 租户配额：命名空间 `ResourceQuota`（含 `<sc>.storageclass.storage.k8s.io/requests.storage`）；邻居噪声治理通过 cgroup `io.max` 等 IO 限速作为可选能力，POC 评估。
7. 加密：如有合规要求，LUKS 放在 LV 之上（或 TopoLVM 支持的方式 `【待核实】`），密钥管理纳入范围评估。

## 7. Go 控制面设计

| 控制器 | 监听 | 核心逻辑 |
| --- | --- | --- |
| disk-ctrl | Disk、Node | 汇总健康；节点失联超过阈值（默认 30min，可配）→ 标 stale，触发 §9.2 |
| vg-ctrl | VG、Disk | 声明式 reconcile：创建 StorageTask；保护锁；冗余降级检测 |
| capacity-ctrl | VG、ThinPoolPolicy | 阈值/预测评估、`capacityStatus`、滞回、告警、渲染 lvm.conf 的 autoextend 配置 |
| lvmd-config-ctrl | VG | 渲染并灰度下发 lvmd device-class 配置 |
| lifecycle-ctrl | StorageNodeOps | 节点退役/隔离/盘迁移状态机 |
| backup-ctrl | VolumeSnapshot | 备份任务编排，见下 |
| orphan-gc | PV、LogicalVolume、lvs | 检测 **Retain 后 Released 的 PV 与孤儿 LV**，统计占用，提醒人工回收（Retain 的长期隐形容量成本） |
| drift-detector | CR / PV / lvs | 发现人工 `lvcreate/lvremove` 等绕过平台的变更，告警并给出"补录/回滚"建议；提供 break-glass 流程（授权窗口内允许手工操作并事后补录） |
| audit | 所有写操作 | 操作人、对象、前后值、时间、来源；同时依赖 K8s audit log，二者可交叉校验 |

**备份实现建议**：快照由 TopoLVM CSI 完成；导出对象存储**优先采用成熟方案**（Velero + CSI 快照 + Kopia/Restic 数据移动），而不是自研导出 Job。若自研，需处理：从快照恢复出临时 PVC 并绑到同节点、块/文件系统一致性、增量与去重、限速以免挤占业务 IO、失败重试与完整性校验。**必须包含恢复演练与 RTO/RPO 验证**，没有被验证过的备份不算备份。

**节点故障污点（修正）**：v1.0 使用自定义 `NoSchedule` 污点会使整个节点对所有 Pod 不可调度，范围过大。改为：存储故障标签 + §4 的调度约束注入；节点 NotReady 本身由 K8s 内置污点处理。

| 告警 | 级别 | 条件 | 动作 |
| --- | --- | --- | --- |
| ThinPool data ≥75% | Warning | 持续 5min | 通知；检查 autoextend 是否生效 |
| ThinPool data ≥85% | Critical | 立即 | 置 locked + 通知（扩容由 dmeventd/capacity-ctrl 执行） |
| 距写满时间 < 24h / < 4h | Warning / Critical | 增长速率预测 | 通知 |
| metadata ≥50% / ≥75% | Warning / Critical | — | 通知；元数据扩容预案 |
| pool 进入 out-of-space 或 `needs_check` | Critical | 立即 | 进入 Runbook §9.1 |
| VG free < 阈值且无法扩容 | Critical | — | 转人工工单 |
| SMART Failed / `critical_warning≠0` / available_spare 低于阈值 | Critical | 立即 | 标记盘；无 RAID 明确告知数据风险；有 RAID 启动换盘流程 |

| webhook 异常 / 控制面 leader 丢失 | Warning | >2min | 通知（数据面不受影响，见原则 4） |

## 9. 故障标准剧本（Runbook as Code）

### 9.1 ThinPool 打满（最高危）

1. **预防优先**：autoextend + 分级超分 + 锁；定期审计超分比例。
2. 越限：capacity-ctrl 置 `locked`（拦截新 PVC 与扩容，调度层排除该节点）；dmeventd 尝试扩容（如 `lvextend -L +<size> <vg>/<pool>`，具体参数以 lvmthin(7) 为准 `【待核实】`）。
3. VG 空间不足：告警转人工。预案：对可回收卷执行 **`fstrim`** 归还空间；清理已确认的临时/孤儿 LV（`lvremove`，需审批）；临时挂盘 `vgextend`。**不使用 `lvreduce` 缩小有数据的 thin LV**（v1.0 写法有数据损坏风险）。
4. 已进入 out-of-space：pool 可能转为只读/错误返回，先扩容再恢复，随后运行 `thin_check`，评估文件系统一致性（XFS 修复需业务停写、先备份）。
5. 事后分析：超配审计 + 下调建议。

### 9.2 节点整机故障

1. disk-ctrl 判定失联（默认 30min）→ 创建 `StorageNodeOps(isolate)`，打存储故障标签。
2. 多副本业务：UI 展示受影响 PVC，生成"重建 PVC 到新节点"的工单模板（含业务确认）。注意本地 PV 带节点亲和，Pod 会一直 Pending，需删除旧 PVC/PV 才能重建；Retain 的 PV 需人工处理。
3. **旧节点恢复后不自动删除残留 LV**（修正 v1.0 的自动清理）：进入"隔离期"（默认 7 天，可配），由人工确认数据已不再需要或已重建一致后，再通过 `StorageTask` 清理。理由：自动删除不可逆，且恢复后的旧数据可能是唯一完好副本。
4. `recover-disk`：新节点识别 foreign VG → 人工确认 → `vgimport`，校验 LV 与 PV 对应关系；**全程人工确认，不自动迁移数据**。

### 9.3 VG 内磁盘损坏

- **无 RAID**：`pooled` 布局下该 VG 全部 LV 不可恢复（`per-disk` 布局仅影响单盘）。流程：Critical 告警（明确文案）→ 业务从其他副本重建 → 经审批的 `StorageTask` 执行 `vgreduce --removemissing`（`--force` 仅在确认后）→ 换盘后重新纳管（走 Disk 状态机，不复用旧对象）。
- **有 RAID（硬件/md）**：降级告警 → 换盘 → 重建 → 监控重建进度与重建期间性能；LVM RAID 场景以 `lvconvert --repair` 为准 `【待核实】`。

### 9.4 节点退役

`StorageNodeOps(retire)`：`validate（列 PVC）→ drain（等待业务确认）→ wait-pvc-cleanup → wipe（可选）→ done`。阻塞点写入 `status.blockingPVCs`；存在在用 PV 时通过 webhook 拒绝删除节点相关存储对象（含 finalizer 保护）。

## 13. 取舍与精简路径（新增）

**为什么不直接 TopoLVM + Prometheus 规则 + 运维文档？** 这是最低成本的基线，本方案相对它的增量为：磁盘预检与纳管（防误操作）、容量治理闭环、状态机化的故障剧本、统一审计。需在立项评审中明确这些增量是否值得"自研控制面"的长期维护成本。

**精简路径（若人力/周期受限）**：阶段 1 只做 ① exporter + 告警规则（含预测告警）、② lvm.conf autoextend 标准化、③ Disk 只读发现 + 预检报告、④ 静态 ValidatingAdmissionPolicy；暂缓自研 webhook、StorageTask 写路径、lifecycle 与备份编排（备份用 Velero）。待 POC 与线上数据证明必要性后再补全。

**关键决策汇总**

1. CSI 用上游 TopoLVM，控制面 Go；agent 语言过决策门。
2. CRD 声明式 + StorageTask 单写路径 + 分层单写者。
3. 容量保护以"分级超分 + dmeventd + 锁 + 预测"为主，自动扩容只是缓冲。
4. POC 先行，指标以实测定标。
5. 破坏性操作必须人工确认，数据面独立于控制面。

## A.2 相对 Carina 的增量

1. **快照/克隆/备份**：继承 TopoLVM 的 CSI 快照，叠加跨存储的备份闭环（本地快照本身不防盘损）。
2. **容量治理深度**：超分分级、预测告警、锁与调度约束，将"防止 thinpool 被写爆"做成一等能力。
3. **演进自主性**：控制面由平台掌握节奏，代价见 A.3。

## A.3 需要承认的短板

1. 控制面是自研软件，**升级、故障、兼容矩阵的责任在平台团队**。
2. 无跨节点副本：数据 HA 依赖 RAID + 业务多副本。
3. 差异化组件无社区背书，质量依赖自身测试体系，混沌演练为上线门禁。
4. 性能优势需 POC 数据支撑，不应在文档中预先承诺。

## A.4 一句话定位

> 本方案是"以 TopoLVM 为供给引擎的磁盘生命周期与容量治理系统"：与同类本地 LVM 存储同档性能与成本，多付一份控制面维护成本，换取磁盘纳管防误操作、thinpool 防爆、故障剧本自动化和自主演进节奏。
