# hlvm v0.1.0-preview.3

**定位：技术预览版（Developer Preview）。用于集成联调、方案评估与内部汇报，禁止用于生产环境。**

第三个技术预览版，范围很窄：**修复 B 链路（TopoLVM CSI）一个会导致供给与容量双双错误的产品缺陷**，并让修复能以发布版镜像部署到真机。它不是功能增量版本。

## 1. 本版解决了什么

`AggregateLVMDConfig` 渲染的 lvmd device-class 只有 `thin-pool:` 段，缺 `type: thin`。
TopoLVM v0.42.0 的 `NewDeviceClassManager` 仅在 `dc.Type == TypeThin` 时注册 thin-pool；
`type` 为空会被归一为 **thick**，thin-pool 配置整段被忽略。后果：

- 容量按 `vg_free` 上报，两节点各只有 2 GiB，而实际建好的 thin-pool 是 36G；
- PVC 创建的是 thick LV（直接从 VG free 切），并非 thin LV；
- 上一版 E2E 只检查「VG 内新增 1 颗 LV + 尺寸」，无法区分 thick/thin，因此
  「thin LV 验收 PASS」属于**判据假绿**。

真机可逆 A/B 实证（控制器临时停 reconcile、3 份 ConfigMap 全量备份、实验后恢复基线）：
补上 `type: thin` 后，两节点容量注解 `2143289344 → 38654705664` B（2 GiB → 36 GiB），
两条 `CSIStorageCapacity` `2044Mi → 36Gi`，新建 LV 的 `pool_lv=thinpool`、
`lv_attr=Vwi-aotz--`（thin volume），回收后无残留。

## 2. 不适用场景（请先读这一节）

- 承载任何生产或准生产数据；
- 作为灰度放量、上线评审或容量规划决策的唯一依据；
- 依赖「已有 thick LV 自动迁移到 thin-pool」的升级路径（本版不迁移存量 LV）；
- 依赖平台自动修复 LVM 漂移（`DriftDetector` 只告警，且 lvs 一侧仍未接入）；
- 依赖 CRD 双版本 conversion webhook 的高可用链路（覆盖情况见 preview.2 说明）。

## 3. 相对 preview.2 的增量

| 域 | 变更 |
|---|---|
| 控制面 | `AggregateLVMDConfig` 每个 device-class 显式渲染 `type: thin`；函数注释钉死 TopoLVM 上游行为与实测数字 |
| 配置快照 | `configmap-lvmd-all.yaml` / `-153` / `-202` 三份同步；`TestLvmdPOCArtifactsConsistent` 逐字节锁定「快照 == 渲染结果」 |
| 判据 | `pvc-supply-e2e.sh` 新增 `lv_pool_of()`：新增 LV 的 `pool_lv` 必须指向 thin-pool，否则 FAIL，堵住假绿 |
| 测试 | `TestAggregateLVMDConfig_SortedAndComplete` 期望串同步 |
| 版本 | `VERSION` / `agent/Cargo.toml` / `agent/Cargo.lock` 三元同步；**未改 Rust 源码** |
| 文档 | ADR-006 §14（缺陷、A/B 实证、修法、边界）、ADR-007 §5 容量边界更正、CHANGELOG |

自 preview.2 以来 `main` 上还包含 B 链路双 worker 扩容（ADR-006 §13）：
聚合 ConfigMap + initContainer 按 `NODE_NAME` 投影、三个 DS 改标签选择器、
修复多节点下 `kubectl exec ds/...` 任取 Pod 的判据缺陷。该轮未改产品代码，
本版是其后第一个带控制器代码变更的发布。

## 4. 升级注意

1. **必须更新控制器镜像**：`LvmdConfigReconciler` 用
   `Owns(ConfigMap, MatchEveryOwner)`，任何手工修改的 ConfigMap 都会被旧渲染结果覆盖。
   只改 ConfigMap 不换镜像等于没修。
2. 部署 `storage-controller:v0.1.0-preview.3` 后，让控制器重渲染 per-node ConfigMap
   （删掉托管 CM 或触发 NodeVG 事件），再用 `expand-lvmd-nodes.sh` 同步聚合 CM，
   最后重启 lvmd DS 使新配置投影生效。
3. 切换后**新建** LV 走 thin-pool；切换前已存在的 thick LV 不自动迁移。
   若存量环境已有 PVC，需逐个评估，不要在带数据的 VG 上直接切换。
4. `overprovision-ratio` 仍默认 `1.00`（不超供给），容量上限是 thin-pool 36G；
   要超供需显式调大 `NodeVG.spec.thinPool.overprovisionRatio`。

## 5. 验证与已知边界

仓库侧验证（打 tag 前已完成）：Go `vet ./...` + `test ./...`、Rust
`cargo test --all-targets`（155 passed）、全部脚本 `bash -n`、`git diff --check`、
`VERSION` / `Cargo.toml` / `Cargo.lock` 三元一致、CI 全 job。

真机侧已完成的是**可逆 A/B 实证**（§1 表格；控制器临时停 reconcile、3 份
ConfigMap 全量备份，实验后已恢复 2 GiB 基线且无残留 PVC/PV）。修复随发布版控制器
镜像部署后的双节点 PVC E2E 复验，按 §4 在目标集群执行，**不作为「打 tag 前已通过」
宣称** —— 它需要本版镜像先产出，时序上必然晚于 tag。

仍未闭合（详见 ADR-006 §13.5 / §14.5）：

- `NodeVG` 仍是手工 seed；`LVReporter` 未接。接线前需先修 `DriftDetectorReconciler`
  把 `pv.Name` 当作 managed LV 名的问题（TopoLVM 实际 LV 名是另一个 UUID），
  否则接上 lvs 上报会产生 `unmanaged-lv` 与 `missing-lv` 双向误报。
- 聚合 ConfigMap 仍由脚本同步，控制器只渲染 per-node ConfigMap。
- 只覆盖 2 个 worker；控制面节点未扩，A 链路设备插件仍只在单节点。
- 未跑 `m15 all`：`verify-agent` 相位会删除常驻 agent DaemonSet、若干相位仍假设单节点。
- 备份恢复（Velero）、热插拔、kubelet 重启的 checkpoint 断言在真机因环境能力缺失为 SKIP，
  **不计 PASS**。

本版为预发布（prerelease），不提供从 preview.2 的自动数据迁移。
