# hlvm v0.1.0-preview.2

**定位：技术预览版（Developer Preview）。用于集成联调、方案评估与内部汇报，禁止用于生产环境。**

第二个技术预览版。它要解决的问题不是「新增了多少功能」，而是：自 `v0.1.0-preview.1`
以来 `main` 上已累积 7 个提交、83 个文件变更，却一直没有一个可复现的显式版本标签；
同时 CRD 版本化已从 1 个 Kind 扩到全部 5 个 Kind，而发布文档仍写着相反的事实。
本版把代码、文档、镜像标签三者重新对齐，并如实登记仍未闭合的验证缺口。

## 1. 不适用场景（请先读这一节）

以下用途本版本**明确不支持**，请不要尝试并据此评估产品：

- 承载任何生产或准生产数据；
- 在真实 LV / thinpool 硬件上做容量与故障演练，并引用其结果做决策；
- 作为灾备方案的一部分（备份恢复闭环未验证）；
- 灰度放量与上线评审的依据；
- 依赖 v1alpha1 老客户端的高可用链路（conversion webhook 的集群覆盖见 §4）。

## 2. 相对 preview.1 的增量

| 域 | 变更 |
|---|---|
| CRD 版本化 | **5 个 Kind 全部双版本化**：`NodeDisk` / `NodeVG` / `StorageTask` / `StorageNodeOps` / `ThinPoolPolicy` 均为 v1beta1(storage) + v1alpha1(served) + conversion webhook；`config/hardening/03b~03f` 为叠加清单 |
| 消费者 | 控制器 / webhook / dashboard / Rust agent 全迁 v1beta1，conversion 脱离控制面关键路径；`crd-conversion` 启动自检覆盖 5 个 Kind；新增 9 个双向转换往返测试 |
| 集成脚手架 | 新增 `preflight` 只读体检（结构性缺失 FAIL / 能力缺失 WARN）；新增 `M15_SINGLE_NODE=1` 显式单节点模式；修 `all` 在全新集群上的顺序缺陷；`real` 模式拒绝 `IMG_TAG=latest` |
| 回归修复 | 修 11-03 消费者迁移遗留的脚本缺口：7 处普通相位仍用 `v1alpha1` 建 `NodeVG`/`StorageTask`、1 处 `ownerReference.apiVersion` 断言仍期望 `v1alpha1`，导致 `all` 在 `verify-admission` 失败；conversion 相位中刻意使用 v1alpha1 的断言保持不变 |
| 设备身份 | `/dev/disk/by-id` 多别名按前缀优先级择优，消除同盘两次枚举得到不同 ID 的身份漂移 |
| 调度 | 控制面三组件软 `topologySpreadConstraints`；PDB 改 `maxUnavailable: 1`，随副本数缩放 |

代码层能力（磁盘/VG 对账、纳管状态机、容量治理、准入控制、device plugin、可观测性）
与 preview.1 相同，本版未新增产品功能。

## 3. 验证到什么程度

| 验证面 | 环境 | 结果 |
|---|---|---|
| Go 静态与单测 | 本地 Go 1.27，`go vet ./...` / `go build ./...` / `go test ./...` | 全绿；177 个测试函数 |
| 控制面 e2e | envtest 1.36.2（真实 kube-apiserver + etcd，独立 `config/crd/envtest`） | 全绿 |
| Rust 单测 | `cargo test --all-targets`（CI rust job；本机无工具链） | 146 个用例，CI 全绿 |
| 集成端到端 | WSL2 kind 1.36.4，单节点（显式 `M15_SINGLE_NODE=1`） | 116 PASS / 0 FAIL，exit 0（见 §3.1） |
| CI | GitHub Actions：Go / Rust / 4 镜像 / Ready | 全绿 |

集成断言的判据是**退出码 0 + 无 `FAIL:` / `[error]` + 每个相位打出收尾 PASS 汇总行**；
条数会因环境分支（SKIP 与否）浮动，不要把不同时间的条数相减当作回归判据。
`verify-velero` 在本机两种拓扑下均 SKIP（docker.io / quay 镜像拉取受限），不计入通过。

### 3.1 本次发版的集成回归

`M15_SINGLE_NODE=1` 单节点形态，WSL2 kind 1.36.4（1 CP，无 worker），
`scripts/m15-wsl.sh all` **退出码 0**，日志共 **116 条 PASS / 0 条 `FAIL:` / 0 条 `[error]`**，
14 个相位均打出收尾汇总行：

| 相位 | 结果 |
|---|---|
| `preflight` | 5 PASS / 4 WARN / 0 FAIL（能力缺失按设计只 WARN） |
| NodeDisk 收敛基线 / admission / controller / lvmd / taskgc / ttl | 全部 PASS |
| agent / device-plugin / collector / kubelet-restart / device-hotplug | 全部 PASS |
| conversion（12 条）/ cert-rotation（16 条）/ storage-migration（15 条） | 全部 PASS |
| `verify-topology-scale` | SKIP（单节点显式开关，无跨节点对象可验） |
| `verify-velero` | SKIP（本地拉不动所需镜像） |

**本次回归暴露并修复了 11-03 消费者迁移遗留的脚本缺口**（7 处普通相位仍以 v1alpha1
建 `NodeVG`/`StorageTask`、1 处 ownerReference 断言仍期望 v1alpha1），详见 §2。
修复前 `all` 会在 `verify-admission` 直接失败，说明 11-03 之后到本版之前这段时间里
集成脚本与主分支代码并不兼容——这也是本版必须先跑通 `all` 再发版的原因。

**覆盖边界**：多节点形态本次未重跑。WSL 环境在 3 节点拓扑下 kubeadm 初始化持续超时
（`unable to create ClusterRoleBinding: context deadline exceeded`），改用显式单节点开关完成回归；
上一可复现的多节点基线为 2026-11-03 的 126 PASS / 0 FAIL。跨节点调度断言本版未复验。

## 4. 未验证清单（本版本最大的风险）

| # | 项 | 为什么没验 | 影响 |
|---|---|---|---|
| 1 | 真实 LV / thinpool 行为 | 本地无块设备与 LVM 栈，kind 用 loop 设备模拟 | 容量治理、dmeventd 自动扩容、打满演练、告警延迟全部未实测 |
| 2 | `/dev/disk/by-id`（udev）真机路径 | kind 节点无 udev，只覆盖 `dev-<name>` 回退分支 | 真机设备 ID 形态可能不同，纳管与 device plugin 匹配路径未验证 |
| 3 | Velero 备份恢复闭环 | 本地无法拉取所需镜像，相位 SKIP | RTO/RPO 无数；pre/post hook 与快照一致性未验证 |
| 4 | 节点扩缩容与调度器重平衡 | kind 静态拓扑 | 跨节点调度只覆盖「容量耗尽 / Pending / 回调度」，真实增减节点未验 |
| 5 | 灰度放量与上线评审门禁 | 需真实环境与评审流程 | hardening 5.2 / 5.3、poc V.1-b 仍为空 |
| 6 | 多 apiserver 副本下的 conversion | 单 CP | webhook 高可用与证书在多副本下的行为未验 |
| 7 | **5 个 Kind 的 v1alpha1 兼容层集群验收** | 集成脚本 `verify-conversion` / `verify-cert-rotation` / `verify-storage-migration` 只 apply `03b`（NodeDisk）；`03c~03f` 从未被任何相位 apply | 另外 4 个 Kind 只有单元测试与 envtest（envtest 无 conversion 服务）；集群侧 conversion 链路、证书注入、storedVersions 迁移均未被证明 |

第 7 项是本版新增登记、也是最容易被「5 个 Kind 已双版本化」这句话掩盖的缺口。
**代码完成 ≠ 集群验证完成**；后续里程碑会把 5 份叠加清单纳入集成相位。

## 5. 已知限制

- **Go 侧 K8s 依赖版本错配**：`k8s.io/api` / `apimachinery` 为 v0.33.0，
  `client-go` / `apiextensions-apiserver` 为 v0.32.1；Rust 侧 `k8s-openapi 0.28` 启用 `v1_36`；
  实测集群是 1.36.1、envtest 1.36.2。M14 曾因 envtest 1.33 与 kind 1.36 的版本差漏检过
  VAP 兼容性缺陷，本项作为已知风险登记，不做未经评估的升级。
- **webhook 故障域**：v1alpha1 读写会经过 conversion webhook；该组件故障时 v1alpha1 不可用
  （v1beta1 可读）。控制面消费者已迁 v1beta1，不受影响；请勿在此版本上依赖 webhook 高可用。
- **GHCR 包为私有**，集群侧需注入 `imagePullSecret`（见 runbook §6）。
- **真实集群脚本为首版**：`scripts/real-cluster/*` 只做过语法 / YAML 校验与 kind 侧适配层回归，
  尚未在真实云主机端到端跑过；首次执行请按 README §4 的检查点逐步确认。

## 6. 获取与部署

镜像（请使用显式版本标签，不要引用 `:latest`）：

```
ghcr.io/f31/hlvm/storage-controller:v0.1.0-preview.2
ghcr.io/f31/hlvm/storage-webhook:v0.1.0-preview.2
ghcr.io/f31/hlvm/crd-conversion:v0.1.0-preview.2
ghcr.io/f31/hlvm/storage-agent:v0.1.0-preview.2
```

- 本地 kind 复现：`scripts/m15-integration.sh all`（WSL 入口 `scripts/m15-wsl.sh`），
  步骤与排障见 `docs/m15-integration-runbook.md`。
- 真实集群：`scripts/real-cluster/README.md`（3 台起步，1 CP + 2 worker，K8s ≥ 1.36），
  并显式传 `IMG_TAG=v0.1.0-preview.2`——`latest` 会被 `preflight` 判 FAIL。
- 版本自检：`storage-controller --version` 应输出
  `v0.1.0-preview.2 (commit <sha>, built <ts>)`；`hlvm-agent --version` 输出 Cargo 版本。

## 7. 升级注意（从 preview.1）

1. **顺序**：先 apply `config/hardening/03-crd-conversion.yaml` 并等 webhook 就绪，
   **再** apply `03b~03f`。反序会出现「CRD 要求转换、webhook 还不存在」的不可用窗口。
2. **存储版本判定**只能看 etcd 字节；`status.storedVersions` 只增不减，不能当迁移完成判据。
   K8s 拒绝移除 `storedVersions` 仍记录的版本，收成单版本需按 §10.5 的顺序清理。
3. 双版本 CRD 的 apply 会临时改写对象读路径；`all` 中的 `verify-storage-migration`
   是破坏性相位，升级演练前确认集群内没有他人依赖的数据。
4. 消费者已全迁 v1beta1；显式使用 v1alpha1 的老客户端现在依赖 conversion webhook 可用性。
