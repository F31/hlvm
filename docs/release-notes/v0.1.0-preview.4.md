# hlvm v0.1.0-preview.4

**定位：技术预览版（Developer Preview）。用于集成联调、方案评估与内部汇报，禁止用于生产环境。**

第四个技术预览版，主题是**把「CR / PV / lvs 三方对账」的 lvs 一侧真正接上数据**。
在此之前的版本里 `DriftDetectorReconciler.Reporter` 为 nil、`actual` 恒空，
`DetectDrift` 直接返回空——即三方对账从未实际生效。本版补齐 Rust agent 采集/回写
与 Go 控制面 Reporter/PV watch，并随发布版镜像部署到真机做漂移注入验收。

## 1. 本版解决了什么

| 前置（ADR-006 §15.6） | 本版处理 |
|---|---|
| ① PV → LV 名 / 节点 / VG 映射 | preview.3 之后的 `83499cd` 已修（`ManagedLVsFromPVs`） |
| ② agent 上报侧过滤 thin-pool / 内部 LV | `lvs` 显式取 `lv_attr`、`pool_lv`，按首位 `t/T` 与 `[` 前缀过滤；控制面再加同名兜底 |
| ③ PV 增删改不触发对账 | `SetupWithManager` 增加 `Watches(PersistentVolume)`，映射到全部 NodeVG |
| ④ agent 侧 lvs 采集与回写通道 | 新增第三条常驻循环：宿主 `lvs` → `NodeVG.status.logicalVolumes` + `lastLVReportTime`（`patch_status`） |

同时修掉两个会造成**误报**的隐患，以及一个真机只读验证现场抓到的**既有读路径缺陷**：

- 真机在旧 agent Pod 内按 wrapper 现场执行 `lvm lvs ... --reportformat json
  --reportformat json`，宿主 lvm 返回 `Option --reportformat may not be repeated.`
  （exit 3）。`report_vg/lv/pv` 各自带了这个 flag，`lvm_argv_with` 又无条件追加一次，
  因此 **LVM 读路径此前一直是失败的**（`build_host_state` 静默忽略了 `report_pv()`
  的失败）。本版改为幂等注入并去掉重复 flag，新增 2 个 argv 单测钉死。不修的话，
  新的 LV 上报循环会永远采集失败，控制面因新鲜度门禁整轮跳过对账——表现为
  「升级后零告警」的假绿。
- 采集失败时旧逻辑 `continue`，导致「部分节点有实际清单、部分没有」→ 缺数据节点
  的所有账面 LV 被判成 `missing-lv`。改为任一节点失败即整轮放弃对账。
- `VGReconciler` 用 `Status().Update` 全量写回 `NodeVG.status`；若 Go 类型不声明新字段，
  client-go 解码会丢弃未知字段，下一次 Update 把 agent 上报静默抹掉。本版在
  `VGStatus` 与 deepcopy 中显式声明并加锁测试。

## 2. 不适用场景（请先读这一节）

- 承载任何生产或准生产数据；
- 依赖平台**自动修复** LVM 漂移（`DriftDetector` 只发 Warning 事件 + 补录/回滚建议，
  设计明令 SHALL NOT 自动修复）；
- 依赖「空集群里手工 `lvcreate` 也会被告警」：`DetectDrift` 保持既有契约
  （`managed` 或 `actual` 为空即返回空），**没有 PV 时检不出人工 LV**；
- 依赖 agent 自动创建 / 发现 `NodeVG`：NodeVG 仍由脚本手工 seed，agent 只 patch
  既有 CR 的 status；
- 把 `NodeVG.status.freeBytes` 当成 CSI 可调度容量：它仍是 VG 物理 free 2 GiB，
  与 thin-pool 36 Gi 是不同维度。

## 4. 升级注意

1. **必须先更新 RBAC**：`kubectl apply -f control-plane/config/rbac/agent_role.yaml`。
   否则 agent 的 `patch_status` 返回 403，`NodeVG.status` 永远没有 LV 上报，
   控制面因新鲜度门禁整轮放弃对账（表现为「升级后依然没有任何告警」，而非报错）。
2. **控制器与 agent 必须一起升级**：只用新控制器 + 旧 agent ⇒ 无上报 ⇒ 对账跳过；
   只用新 agent + 旧控制器 ⇒ 上报了但没人消费（且旧控制器 `Status().Update` 会抹掉
   未知字段）。滚动窗口内控制面有 thin-pool 兜底过滤，但**不构成完整对账**。
3. agent 常驻 DaemonSet 必须保留 `HLVM_HOST_WRAPPER=nsenter -t 1 -m -u -i -n -p --`
   （`hostPID: true` + `privileged`）；否则容器内的 lvm 读不到宿主 VG，采集失败。
4. 升级后先确认 `kubectl get nodevg <vg> -o jsonpath='{.status.lastLVReportTime}'`
   在 3 分钟内持续刷新，再跑漂移判据；`lastLVReportTime` 不刷新时任何「零告警」
   结论都不成立。
5. 首次出现 `StorageDrift` 事件只表示对账**开始工作**，不表示集群有故障；
   请按事件里的 LV 名与 `pool_lv` 核对是否为 thin-pool / 历史残留误报。

## 5. 验证与已知边界

打 tag 前仓库侧已完成：Go `vet ./...` + `test ./...` 全绿；Rust
`cargo test --all-targets` **164 passed**；全部 POC 脚本 `bash -n`；`gofmt`；
`VERSION` / `Cargo.toml` / `Cargo.lock` 三元一致；`git diff --check`；CI 全 job。
本轮 4 个改动的 Rust 文件已单独 rustfmt；`cargo fmt -- --check` 仍对
`common/mod.rs` / `plugin/mod.rs` 报既有基线差异（rustfmt 1.10 新规则，非本轮引入，
CI 该步为质量反馈而非硬门禁）。

真机漂移注入验收在镜像产出后执行完毕（2026-11-12）：控制器 2 副本与两个 worker 的
agent 均切 `:v0.1.0-preview.4`，`deploy-agent-real.sh` 两节点各 **PASS=17 / FAIL=0**
（含 nsenter 真实写门禁），`drift-reconcile-e2e.sh` 在 `10-60-153-100` 与
`10-60-166-202` 各 **PASS=19 / FAIL=0 / SKIP=0**：

| 判据 | 结果 |
|---|---|
| 上报新鲜 / thin-pool 未上报 | 通过（滞后 47s / 9s，`logicalVolumes` 不含 thinpool） |
| 业务 LV 按 `volumeHandle` 上报 | 通过（两节点各 1 颗） |
| 正常态零误报 | 通过（基线后 0 条） |
| 手工 `lvcreate` 命中 `unmanaged-lv` | 通过（事件 + 控制器日志均含 LV 名） |
| 无 `missing-lv` 双向误报 | 通过 |
| 清理后告警停止 | 通过（计数 3→3 / 4→4） |
| 回收无残留 | 通过（无 PVC/PV/LV，终态仍在上报） |

首跑时判据自身有一处假红（`awk ... <<< ""` 把空集计成 1 条告警，证据串为空），
已在脚本中修复并复跑验证；这不是产品误报。

真机部署的现实约束：云主机直连 `ghcr.io` 仅约 27 KB/s（agent 压缩 376 MiB 按此速率不可行），
且 `certs.d` 只配了 `docker.io` / `registry.k8s.io`。用
`ctr -n k8s.io images pull --hosts-dir` 指向 `ghcr.nju.edu.cn` 临时镜像源即可（仅拉 10.6 MiB
差异层，秒级），不必改全局 containerd 配置。细节见 ADR-006 §16.6。

仍未闭合：NodeVG 手工 seed、聚合 ConfigMap 脚本同步、只覆盖 2 个 worker
（CP 未扩、A 链路设备插件仍单节点）、`m15 all` 未跑（`verify-agent` 会删除常驻 DS）、
备份恢复/热插拔/kubelet 重启 checkpoint 断言在真机因能力缺失为 SKIP。
另外两点需要换环境时注意：真机 CRD 的 `status` 依赖
`x-kubernetes-preserve-unknown-fields: true` 才能容纳新字段，而仓库
`config/crd/bases` 是 `status: {}`（空 schema 会 prune），**不要直接 apply 覆盖**；
agent 写失败超过 3 分钟时对账会静默停摆，目前只有 `lastLVReportTime` 停滞可观测，
尚未接入该指标告警。

本版为预发布（prerelease），不提供从 preview.3 的自动数据迁移。
